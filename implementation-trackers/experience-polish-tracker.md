# Experience polish tracker

Goal: the existing app should feel good to use. Interactions respond immediately and end cleanly, failures are visible
and actionable, performance holds during every workflow, and the codebase has one implementation of each concept.
The visual design stays as it is: no restyling, new layouts, or new visual surfaces without explicit approval.

Sources: `implementation-trackers/experience-audit/01–08` (read-only audits, 2026-10-14). IDs below match those files.
Validation for every item: E2E/browser-observable checks using the repository's Chromium `*.browser.test.ts`
pattern where behavior is involved; focused typecheck and lint for every change. No unit tests are added.

- [x] AE-03: run the true-peak scan off the main thread or in bounded chunks.
  - Evidence (2026-10-15): `scanTruePeakAsync` (`true-peak-scanner.ts`) scans 4096-frame chunks with the unchanged kernel, checks abort at each chunk, and yields through `yieldToEventLoop` (`event-loop-yield.ts`). Export validation awaits it. Peak bits and all 30 ceiling decisions (6 buffers × 5 ceilings) match HEAD. Longest synchronous block on a 4 s stereo buffer: 86.6 ms → 2.3 ms. Abort rejects 0.026 ms after firing. `acceptance-reports/daw-experience-batch3-perf-2026-10-15.md`.
  - Failure modes (written before the change, 2026-10-15; mode 6 was checked with yield-to-yield block timing, not an event-loop lag ticker):
    1. Measured peak differs from the synchronous scan. A chunk-local sample window would drop oversampling taps at chunk edges. Guard: the kernel keeps reading the full channel array, and the test puts peaks on chunk edges and compares peak bits with the synchronous scan.
    2. Peak differs because each chunk resets the running maximum. Guard: the running peak carries across chunks.
    3. Abort is ignored. The chunk loop does not check the signal, so a cancelled export scans to the end. Guard: check at the top of every chunk and after the last chunk.
    4. Abort is delayed. The check runs only every N chunks, or only after the yield resumes, so extra chunks run after cancel. Guard: check before each chunk's work.
    5. Ceiling decision changes. Silence, NaN handling, or the +0.10 dB tolerance drifts. Guard: the assertion function and its comparison stay as they are, and the test compares decisions on both sides of the tolerance.
    6. Event loop still blocks. A chunk is too large, or a yield is created but not awaited. Guard: 4096-frame chunks, `await` on every yield, and a measured longest event-loop lag.
    7. Runtime without MessageChannel breaks the yield. Guard: the helper is the one media-pages already uses. Bun and Node both expose `MessageChannel` globally, and the benchmark records that check.
    8. Silent pass. The async assertion is not awaited at the export call site, so a rejected ceiling check becomes an unhandled promise and the export passes. Guard: the call site awaits, and the check confirms a too-hot buffer still rejects the export.
    9. Not applicable: the batch kernel has no history state across frames. The streaming scanner's ring buffer does not apply to this path.

- AE-08 (new): live graph edits never interrupt audio. Design note: `implementation-trackers/experience-audit/10-audio-host-graph-updates.md`. Decisions:
  - Scope: full fix. Adding, deleting, or undoing tracks, effects, VSTs, or routing never restarts the native host, and unaffected audio keeps playing with no gap, voice reset, or tail reset.
  - No fallback. Every edit applies live, including latency changes and VST inserts or removals. Deferring an edit, rejecting it, or interrupting audio briefly are all unacceptable.
  - Deleting a sounding track or effect cuts its own sound immediately. No tail decay.
  - While recording, unrelated edits are allowed. The record target cannot be deleted or rerouted until Finish, and the UI explains why.
  - The plan goes to the user before implementation.
  - Plan: `implementation-trackers/ae-08-live-graph-edits-plan.md`. Opus review: `implementation-trackers/ae-08-plan-review.md` (go for phase 1; no-go for phase 3 until the latency policy is rewritten).
  - Latency (user, after review): adaptive budget. Total output latency equals the current maximum path latency. When an insert raises it, the whole mix gets one short fade of about 5 ms. When it would drop, the drop waits for the next transport stop, which is inaudible. Unaffected tracks are otherwise sample-identical. Armed or monitored tracks skip compensation, like Ableton's Keep Latency.
  - Latency raise (user: "closest to Ableton"): when an insert raises the maximum by R frames during playback, the whole mix shifts R frames later. That is a brief repeat, about 43 ms for a 2048-frame plug-in at 48 kHz, masked by the 5 ms fades. No extra headroom and no slowdown, matching Ableton, which keeps latency equal to the maximum plug-in latency.
  - Deleting a sounding object fades it out over about 5 ms (time-based, not a sample count) instead of a hard cut.
  - VST insert: the device shows at once and joins when ready. The plug-in loads once (cache the preflight result). Deleted instances stay parked for a bounded time, so undo of a delete is instant. No pre-warmed idle workers.
